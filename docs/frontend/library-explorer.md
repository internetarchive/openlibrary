# Library Explorer (incl. Genre Explorer)

> **Status:** partial — Library Explorer (DDC/LCC) is shipped and stable; Genre Explorer is an unmerged spike/prototype as of this writing (branch `13158/feature/genre-explorer-spike`, issue #13158), still mid-iteration on its scroll/gesture UX.
> **Sources:** direct code reading + a long live debugging session (2026-07-22/23) implementing the Genre Explorer prototype
> **Last ingested:** 2026-07-23

A Vue 3 web component (`<ol-library-explorer>`) that lets a reader browse the catalog as a virtual bookcase, organized by classification scheme — Dewey Decimal (DDC), Library of Congress (LCC), and (prototype) genre/subgenre. Reachable at `/explore` (DDC/LCC) and `/explore/genres` (genre mode).

---

## How It Works

**How the Vue → `<ol-library-explorer>` build works is generic to every Vue component in this codebase, not specific to Library Explorer — see [[frontend]]'s "Vue component pipeline" section** (Vite, `customElement: true`, the `isCustomElement` predicate that lets these templates use Lit's `<ol-*>` tags directly) rather than duplicating it here.

`LibraryExplorer.vue` is the root component. It builds a `classifications` array — one `ClassificationTree` object per scheme:

```js
{
  name: 'ddc' | 'lcc' | 'Genre',
  longName: string,
  field: string,              // Solr field this scheme queries against ('ddc', 'lcc', 'subject_key')
  fieldTransform: fn,         // raw Solr value -> display label
  toQueryFormat: fn,          // jumpTo string -> query-ready string
  chooseBest: fn,             // pick the "canonical" value when a book has several for this field
  supportsPreciseJump: bool,  // false for genre -- no `${field}_sort` Solr field exists to rank within
  alphabeticalTopNav: bool,   // true only for genre -- top nav is an A-Z strip, not prev/next
  root: ClassificationNode,   // the tree itself
}
```

Each scheme's tree is a static JSON file (`ddc.json`, `lcc.json`, `genre.json`) imported at build time — webpack bundles them, no runtime fetch. Every node is a `ClassificationNode`:

```js
{ name, short, query, hierarchyQuery, count, children }
```

- `query` — bare Solr query fragment for this node. Format differs by scheme (all three are prefix-wildcard style, but against different Solr fields): DDC `"00*"` (digit prefix, queried as `ddc_sort:00*`), LCC `"B--*"` (letter + dash-padded prefix, `lcc_sort:B--*`), genre `"crime*"` (a `subject_key` slug, `subject_key:crime*`).
- `hierarchyQuery` — **genre.json only** (confirmed zero occurrences in `ddc.json`/`lcc.json`; the `ClassificationNode` typedef comment in `utils.js` says so explicitly). An **ancestor-prefixed** version of `query` (e.g. `"absurd/surrealism*"`), needed only because a genre subgenre can have multiple parents, so `query` alone can't disambiguate which parent a `hierarchyFind`/`findClassification` match belongs to. DDC/LCC are strict single-parent trees, so `query` alone suffices there. Critically, a bare/non-prefixed value (like a raw URL slug) will **not** match `hierarchyQuery` and silently resolves to nothing (see Common Confusion below).

`BookRoom.vue` renders the actual bookcase(s) from `classification.root`. `Bookshelf.vue`/`Shelf.vue`/`OLCarousel.vue` render each shelf level down to the book carousel, which lazy-loads via `IntersectionObserver` once scrolled near viewport.

### Data provenance: ddc.json/lcc.json vs. genre.json

The three files are loaded identically (static, build-time JSON) but produced completely differently:

- **`ddc.json`/`lcc.json` are not generated by any script in this repo, at all.** They were added wholesale in commit `32cf17594` ("Copy paste library explorer from my codesandbox", Drini Cami, 2020-09-23) as a one-time hand-copy from an external CodeSandbox prototype. Every commit touching them since (`64bbff4d7`, `605542389`, `f5c0e4943`, `e806ae942`) is a direct manual JSON edit — none references a source script or regeneration process. Their `count` values are frozen at whatever they were when copied/last hand-edited, not live-refreshed.
- **`genre.json` is generated** by `scripts/generate_genre_classification.py` (see below), which live-verifies every count against production Solr at generation time. Its own docstring explicitly frames its output as matching "the same shape as ddc.json/lcc.json" — shape-compatible, not provenance-compatible.

Practical implication: if DDC/LCC counts ever look stale or wrong, there is currently no regeneration command to run — fixing them means hand-editing the JSON directly, the same way past fixes did.

### DDC/LCC mode vs. Genre mode, and why they differ

| | DDC/LCC | Genre |
|---|---|---|
| Bookcases on screen | Many, continuous — scroll reveals the next sibling | Exactly **one** (`bookcases` computed returns `[this.activeRoom]`, not `this.activeRoom.children`) |
| Switching mechanism | Native horizontal scroll-snap (`scroll-snap-type: x mandatory` on `.book-room-shelves`, `scroll-snap-align: center` on `.bookshelf-wrapper`) | Alphabetical top nav (`GenreTopNav.vue`) or explicit swipe/wheel gesture (`selectAdjacentGenre`) |
| Ordering | Classification number — has a natural numeric adjacency (610 sits next to 620) | Genre *name* — "Comedy" has no adjacency relationship to "Crime" |
| `supportsPreciseJump` | `true` — `ddc_sort`/`lcc_sort` are real, rankable Solr fields | `false` — no equivalent sortable field exists for `subject_key`, so there's no way to jump to a precise position *within* a shelf, only to the shelf itself |
| Filter/sort controls | `LibraryToolbar.vue`, a shared floating bottom toolbar | `GenreFilterBar.vue`, its own always-visible top bar (Readable Only / Language / Audience / Fiction-Nonfiction / Tags / Length / Sort), built from the site's real Lit component library (`ol-toggle`, `ol-select-popover`, `ol-options-popover`) — `LibraryToolbar.vue` is explicitly hidden in genre mode |

**Why the architecture actually differs, not just the numbers**: DDC/LCC classification numbers form one continuous, ordered range — "scroll past the edge of the current bookcase" is a coherent gesture because there's always a well-defined *next* number. Genre names have no such intrinsic order; "next genre" only means something once you've picked an ordering (alphabetical), so genre mode needs an explicit selection UI (the A-Z top nav) rather than being able to reuse DDC/LCC's continuous-scroll-through-siblings model. This is also why a genre and its subgenres are shown as a single, complete bookcase rather than one sibling among a continuous strip: a genre's subgenre list is a small, curated, complete set (a genre might have 10-15 subgenres total), not an arbitrarily-continuable range the way DDC ranges are — there's no "next" bookcase over from "Crime" the way there's a next DDC bookcase over from `61X`.

The separate filter bar exists because slicing by audience/length/rating is more central to genre-driven fiction discovery than to DDC/LCC's classification-structure browsing — it was built as its own persistent top bar per the original feature request, deliberately not folded into (or replacing) DDC/LCC's existing bottom toolbar.

### jumpTo (deep linking)

Two mechanisms, deliberately separate, not merged:

- **`?jumpTo=field:value`** — query param, resolved once at initial mount (`findClassification` in `BookRoom.vue`, using `hierarchyQuery` matching). Changing it implies a full page reload in this server-rendered shell.
- **`#value`** (genre mode only) — hash anchor, reacted to live via a `hashchange` listener (`onHashChange` in `BookRoom.vue`), no reload. Added specifically so a homepage genre link can jump the already-open app to a genre/subgenre without a full navigation. Resolved via `findGenreNodeBySlug` (bare `short`-slug equality), **not** `findClassification` — see Common Confusion.

## Why It Exists

Open Library's catalog has no native "browse by shelf" experience — Library Explorer gives readers a spatial, physical-bookcase metaphor for discovery instead of pure search. Genre Explorer (#13158) extends the same mechanism to genre/subgenre browsing, since DDC/LCC classification doesn't map to how most readers think about fiction ("I want a mystery," not "I want 813.087").

## How It Is Used

```bash
# Regenerate genre.json from the Open-Book-Genome-Project/tags vocabulary
python scripts/generate_genre_classification.py
python scripts/generate_genre_classification.py --source github --skip-counts   # skip live Solr count verification

# Rebuild the compiled Vue bundle after any .vue change (required — no hot reload in this dev setup)
docker compose run --rm home make components
```

Local dev's Solr index is too sparse to meaningfully test book counts/filters — verify against production instead: append `&ol_base=openlibrary.org` to any Explorer URL to point `CONFIGS.OL_BASE_*` at the real API.

## Subcomponents and Architecture

- **`LibraryExplorer.vue`** — root; builds `classifications`, holds `FilterState`/sort state, resolves initial `jumpTo`
- **`BookRoom.vue`** — the actual bookcase renderer; genre-mode navigation logic (`switchActiveRoom`, `selectAdjacentGenre`, wheel/touch gesture handling) lives here
- **`Bookshelf.vue`** — one bookcase's shelves; owns the genre-to-genre cross-slide CSS transition and its height-pinning hooks (`onBeforeLeave`/`onEnter`/`onAfterEnter`)
- **`Shelf.vue`** — one shelf (one subgenre/DDC-range); wraps `OLCarousel`
- **`OLCarousel.vue`** — the book carousel; owns the `IntersectionObserver`-based lazy fetch and the actual `search.json` query
- **`GenreTopNav.vue`** — genre mode's alphabetical top nav
- **`GenreFilterBar.vue`** — genre mode's filter bar (Readable Only / Language / Audience / Fiction-Nonfiction / Tags / Length / Sort), built from real Lit components
- **`scripts/generate_genre_classification.py`** — synthesizes `genre.json` from the tags vocabulary; see below

### genre.json synthesis

Reads `tag_types/genres/vocabulary.json` and `tag_types/subgenres/vocabulary.json` from a local `Open-Book-Genome-Project/tags` checkout (or fetches from GitHub with `--source github`). A subgenre can have multiple `parent_genres` (e.g. "Apocalyptic" under Horror/Sci-Fi/Fantasy) — it's duplicated once per parent in the output tree, each with a correctly ancestor-prefixed `hierarchyQuery`.

`resolve_subject_key(tag, with_counts)` tries several candidate Solr slugs per term (the vocabulary's own slug, Open Library's own `subject_name_to_key`-normalized form, a hyphen→underscore variant, an explicit synonym override) against **live production `search.json` counts**, keeping whichever candidate returns the most real books — every term in the shipped `genre.json` was individually verified non-zero against production this way.

`EXCLUDED_SUBGENRES` is a second-pass exclusion list: a term can have a healthy *raw* subject count but still resolve to **zero real, visible results** once the app's actual default filters are applied (`has_fulltext:true` from "Readable Only" defaulting on, plus a `first_publish_year:[1985 TO 9998]` range genre mode has no UI control to change) — `resolve_subject_key`'s check doesn't account for this, so these were found and excluded manually after live-testing the running app (e.g. "Kafkaesque", "Gonzo", "Greek tragedy").

`DEMO_SUBGENRE_ADDITIONS` — ~139 demo-only subgenre entries **not** submitted to the real tags vocabulary repo, added because roughly half the genres had 0-2 real subgenres in the vocabulary as it existed at generation time; every term was still individually verified live before inclusion.

## Configuration

`FilterState` (in `LibraryExplorer.vue`) holds `has_ebook`, `languages`, `age`, `year`, `fiction`, `tags`, `length` — each turned into a Solr filter clause by `solrQueryParts()`. `PAGE_LENGTH_RANGES` maps length-bucket keys to Solr range strings (must stay in sync with `GenreFilterBar.vue`'s `LENGTH_ITEMS` labels — two independent constants, not a shared module).

## Testing

No automated test suite for this component tree as of this writing. All verification during Genre Explorer development was manual, via Playwright scripts driving a real headless browser against the running dev server (`http://localhost:8081/explore/genres`), because:
1. The whole app renders inside `<ol-library-explorer>`'s **shadow root** — `page.evaluate` queries need `document.querySelector('ol-library-explorer').shadowRoot.querySelector(...)`; Playwright's own locators pierce shadow DOM automatically.
2. Local dev Solr is too sparse for realistic filter/count testing — real verification needs `&ol_base=openlibrary.org`.
3. **Synthetic wheel-event timing does not reliably predict real trackpad behavior** — see What's Broken below. Several rounds of Playwright-verified gesture-debounce fixes did not hold up on real hardware; do not trust a synthetic wheel-burst test's result as proof a real-world gesture bug is fixed.

## What's Broken / Fragile / Unimplemented

- **Vertical "step one shelf per scroll gesture" (genre mode) is unsolved as of this writing.** Every JS-timing-based approach tried — debounce-to-quiet, leading-edge throttle with a refreshing/capped lock, collect-then-block-until-transition-done, silence-based gesture-active flag — either felt laggy (waiting out a real gesture's momentum tail can take 1-2+ seconds) or let one physical gesture trigger 2-3+ steps, because standard `wheel` events carry no gesture start/end phase and JS can only guess gesture boundaries from event timing, which real trackpad hardware doesn't cooperate with reliably. Currently being reconsidered as native CSS `scroll-snap` instead (letting the browser's own gesture/momentum handling do the work, rather than re-deriving it in JS) — status unresolved.
- **Tags filter (genre mode) reported as producing wrong/unexpected results** — investigated once (data mapping and query-combination logic checked directly against production, both looked correct) but never conclusively root-caused; needs a precise repro (empty shelf vs. wrong books vs. same books) to make further progress.
- **Shelf counts are subject-string prefixes, and some prefixes are topics.** `cult*` is 81% `cultur*`, `psychological*` 83% `psychological_aspects`, while `thriller*` misses the BISAC `fiction, thrillers, …` strings the Tag mapping catches (13× fewer readable Thrillers). The "Readable" toggle (`has_fulltext:true`) also includes ~15% print-disabled-only works. Measured 2026-10-04 in [[genre-shelf-coverage]].
- **`EXCLUDED_SUBGENRES` is a manual, hand-curated list** — there's no automated check that re-verifies "healthy raw count but zero after default filters" the way `resolve_subject_key` verifies raw counts; a future vocabulary refresh could reintroduce a term that needs the same exclusion.
- **`ddc.json`/`lcc.json` have no regeneration mechanism at all** (see Data provenance above) — they're frozen since a 2020 one-time copy-paste, kept current only via direct manual JSON edits. If their counts are ever found stale, there's no script to fix that; someone has to hand-edit the file, same as every prior fix to these two files has done.
- Genre Explorer is not merged/shipped — issue #13158 is explicitly labeled `Needs: Staff Decision` and `Needs: Designs`, and is also independently claimed by a GSoC contributor. Treat this whole prototype as a technical spike, not a reference for "how it will actually ship."

## Common Confusion

- **`hierarchyQuery` vs. bare slugs**: `findClassification`'s matching (`testLuceneSyntax(node.hierarchyQuery, value)`) requires the tested value to already be ancestor-prefixed (e.g. `"horror/vampires"`) to correctly resolve a subgenre — a bare slug (`"vampires"`) never matches and **silently falls back to "All Genres"** with no error. This bit both `?jumpTo=subject_key:<bare-subgenre-slug>` and the new `#slug` hash mechanism. Fix used: a separate `findGenreNodeBySlug` helper (plain `short`-equality search) for anywhere a bare slug is the natural input, leaving DDC/LCC's `findClassification` path untouched.
- **Shadow DOM event retargeting breaks `e.target`-based checks from outside the shadow root.** A `wheel`/`click` listener attached at `window` level (needed to catch gestures anywhere on the page, not just inside the component's own DOM) sees `e.target` retargeted to the shadow *host* element for anything that originated inside the shadow tree — `e.target.closest('.some-inner-class')` will never match, regardless of where the event actually started. Use `e.composedPath()[0]` instead — it's the true originating element, unaffected by retargeting.
- **`IntersectionObserver` + an in-flight CSS `transform` transition is flakier than it looks.** `OLCarousel.vue` already has a documented Chrome-specific note ("Chrome seems to never fire isVisible sometimes") with a partial existing workaround (wait for `el.isConnected` before observing) — but confirmed via a wrapped/logged `IntersectionObserver` that this is *still* insufficient when the element is inserted mid-transition (genre mode's cross-slide): the observer's first callback can report `intersectionRatio: 0` and simply never fire again, even long after the transition settles and the element is genuinely on-screen with normal geometry. Fix used: a `getBoundingClientRect()`-based fallback check on a timer, well after the transition would have settled, that only activates if `isVisible` is still false by then.
- **A site-wide `html { scroll-behavior: smooth; }` rule (`static/css/base/common.css`) silently affects *any* `window.scrollTo()` call anywhere**, including ones that don't pass an explicit `behavior` option. A custom JS-driven scroll animation calling plain `window.scrollTo(0, y)` on every `requestAnimationFrame` tick will have each of those calls independently smoothed/interrupted by the browser, compounding into something much slower and less predictable than the animation's own intended easing. Force `{behavior: 'instant'}` explicitly to bypass this.
- **Vue transition `@enter`/`@before-leave` hooks and `position: absolute`**: an absolutely-positioned element's containing block is its ancestor's *padding* box, not content box — `top: 0` on a `leave-active` class skips past the ancestor's own top padding entirely, causing a visible jump. Fix pattern (see `Bookshelf.vue`'s `onBeforeLeave`): set an inline `el.style.top` to the ancestor's actual computed padding-top, which wins the cascade over the class's `top: 0`.
